# modules/aws/http_api_authorizer

A ready-made Lambda REQUEST authorizer for `modules/aws/http_api`'s `lambda_authorizer` variable. Provisions one Lambda function (plus its IAM role) that:

1. **Always** rejects any request whose `X-Origin-Verify` header doesn't match a generated shared secret. Intended to sit behind a CDN (e.g. CloudFront) that injects this header as an origin custom header, so direct calls to the API's own `execute-api` endpoint -- bypassing the CDN, and whatever WAF/rate-limiting sits in front of it there -- are rejected.
2. **Optionally** (`require_jwt = true`) also verifies the caller's `Authorization: Bearer` token as a JWT against a caller-supplied OIDC issuer, forwarding selected claims into the authorizer context for the downstream integration Lambda to read via `event.requestContext.authorizer.lambda`.

The two "flavors" (origin-check only, origin-check+JWT) are the same Lambda code behind the `require_jwt` toggle, not two separate modules.

## Lambda source

Lambda source is consumed from `@vln-devsecops/http-api-authorizer-lambda` on GitHub Packages (published from [`node-http-api-authorizer`](https://github.com/vln-devsecops/node-http-api-authorizer)) rather than vendored here, so version bumps flow through Dependabot PRs on `lambda-build/package.json` -- the same pattern as `modules/aws/contact_form` and `modules/aws/vlinder_auth`. A `null_resource` installs the package at apply time; `archive_file` then zips the installed `dist/` output. Contract tests mock the archive provider, so they don't require a live npm install.

To install locally before running `terraform validate`/`terraform test`:

```sh
npm install --prefix modules/aws/http_api_authorizer/lambda-build
```

This requires `NODE_AUTH_TOKEN` (a PAT with `read:packages` scope, or `GITHUB_TOKEN` in CI) set for the `@vln-devsecops` scope per `lambda-build/.npmrc`.

## Usage

```hcl
module "authorizer" {
  source = "github.com/vln-devsecops/terraform-modules//modules/aws/http_api_authorizer?ref=v0.1"

  name        = "myapp-prod-admin-api"
  require_jwt = true

  jwt_issuer_url     = "https://cognito-idp.eu-west-1.amazonaws.com/eu-west-1_example"
  jwt_audience       = aws_cognito_user_pool_client.this.id
  jwt_forward_claims = ["tenantId", "permissions"]

  kms_key_arn = aws_kms_key.this.arn
}

module "admin_api" {
  source = "../http_api"

  name = "myapp-prod-admin-api"

  lambda_authorizer = {
    authorizer_uri            = module.authorizer.authorizer_uri
    authorizer_function_name  = module.authorizer.authorizer_function_name
    identity_sources          = ["$request.header.X-Origin-Verify", "$request.header.Authorization"]
  }

  routes = {
    list_users = {
      route_key            = "GET /users"
      lambda_function_arn  = aws_lambda_function.list_users.arn
      lambda_function_name = aws_lambda_function.list_users.function_name
      authorization_type   = "CUSTOM"
    }
  }
}

resource "aws_cloudfront_distribution" "this" {
  # ...
  origin {
    domain_name = regex("https://([^/]+)", module.admin_api.invoke_url)[0]
    origin_id   = "AdminApi"

    custom_header {
      name  = "X-Origin-Verify"
      value = module.authorizer.origin_verify_secret
    }

    custom_origin_config {
      http_port              = 80
      https_port              = 443
      origin_protocol_policy  = "https-only"
      origin_ssl_protocols    = ["TLSv1.2"]
    }
  }
  # ...
}
```

For an origin-check-only authorizer (no JWT -- e.g. a public API you still want to shield from direct `execute-api` access), just omit `require_jwt` and the `jwt_*` inputs.

## Inputs

See `variables.tf`. Only `name` is required; `require_jwt` defaults to `false` (origin-check only). `jwt_issuer_url`/`jwt_audience` are required when `require_jwt = true` -- this isn't enforced by a Terraform validation block, but the Lambda itself fails clearly (`Missing required environment variable: JWT_ISSUER_URL`) if they're left unset while `require_jwt` is true.

## Outputs

See `outputs.tf`: `authorizer_uri`/`authorizer_function_name` (wire directly into `http_api`'s `lambda_authorizer`), and the sensitive `origin_verify_secret` (wire into your CDN's origin custom header).

## Why `random_password`, not the out-of-band Secrets Manager pattern

Some secrets elsewhere in this org's modules (e.g. `vlinder_auth`'s session signing key) are generated by Secrets Manager itself and seeded out of band specifically so the plaintext never becomes a Terraform resource attribute / state entry. That guarantee is structurally impossible here: `origin_verify_secret` is designed to be read back out via a module output and baked into a CDN's static origin config (a Terraform-managed resource attribute), so it ends up in state regardless of how it was generated. Given that's unavoidable, `random_password` gets identical practical exposure with far less machinery -- and its `result` attribute is already marked sensitive by the provider, so it's redacted from plan/apply CLI output.
